# 방송 송출 연속 재생 — 정확하게 하려면 (조언)

> 한 곡 끝나고 다음 곡이 자연스럽게 이어지게 하기 위한 **가장 정확한 접근** 요약. 수십 번 수정해도 결과가 안 나왔다면, **원인을 한 축으로 잡고** 거기서만 개선하는 게 좋습니다.

---

## 1. 현재 구조 요약

- **서버**: 2초마다 `elapsed >= 저장된 곡 길이 + 4초` 이면 다음 곡으로 넘기고, DB 갱신 후 WebSocket으로 `radio_now_playing` 브로드캐스트.
- **리스너**: `nowPlayingMusicId`가 바뀌면 `audioStreamUrl`이 바뀌고, `<audio key={audioStreamUrl}>` 때문에 **요소가 통째로 리마운트** → 새 URL 로드 → **항상 끊김/지연** 발생.
- **곡 길이**: `playlistSnapshot.durationsSeconds[currentIndex]` 사용. 없으면 기본 240초. DJ가 보내는 `currentTrackDurationSeconds`로 보정 가능하지만, **항상 정확히 보내지 않으면** 서버가 잘못된 시점에 다음 곡으로 넘김.

---

## 2. 왜 “연속 재생이 안 된다”고 느끼는가

| 원인 | 설명 |
|------|------|
| **곡 길이 불일치** | 서버가 쓰는 길이(기본 240초 등)가 실제 음원 길이와 다르면, **너무 일찍** 넘기거나 **한참 지나서** 넘김. 그러면 리스너는 “끝났는데 다음이 안 나온다” 또는 “아직 안 끝났는데 다음 곡이 나온다”를 겪음. |
| **트랙 전환 = 새 URL** | 곡이 바뀔 때마다 리스너는 **새 오디오 URL**을 로드함. 로드 + 디코딩 시간만큼 **공백 또는 끊김이 필연**. 구조적으로 “완전 무 gap”은 아님. |
| **진행 시점의 이중화** | “다음 곡으로 넘어갈 시점”을 **서버 타이머**만 쓰면 되는데, DJ 쪽 `ended` 이벤트나 다른 경로가 섞이면, 시점이 어긋나거나 두 번 넘어가는 일이 생김. |

---

## 3. 가장 정확한 접근 (우선순위)

### 3.1 단일 기준: “다음 곡 시점”은 서버만

- **다음 곡으로 넘기는 시점**은 **서버의 elapsed 타이머 하나**로만 결정하는 게 정확합니다.
- DJ 브라우저의 `audio.ended`로 서버를 한 번만 업데이트(다음 곡 ID + `nowPlayingStartedAt`)하고, 서버가 DB 갱신 후 `radio_now_playing`만 보내게 하세요.  
  “리스너가 자기 audio.ended로 뭔가 한다” 같은 이중 트리거는 제거하는 게 좋습니다.

### 3.2 곡 길이를 반드시 정확히

- 서버가 `elapsed >= duration + 버퍼` 로 판단하므로, **duration이 틀리면** 연속 재생이 절대 맞지 않습니다.
- **DJ가 곡을 올릴 때 / 재생이 시작될 때** 실제 재생 길이를 서버에 보내야 합니다.
  - 예: `onLoadedMetadata` 또는 첫 `timeupdate`에서 `duration`을 읽어서  
    `PATCH /api/radio/channels/:slug`  
    `{ currentTrackDurationSeconds: Math.ceil(audio.duration), queueMusicIds: [...], queueDurationsSeconds: [...] }`  
    형태로 반영.
- 서버는 다음 순서로 사용하는 게 안전합니다.  
  `nowPlayingTempDurationSeconds`(DJ가 방금 보낸 값) → `playlistSnapshot.durationsSeconds[currentIndex]` → 기본값(240 등).
- 저장된 `durationsSeconds`는 DJ가 보낸 실제 길이로 **항상 덮어쓰기**해 두면, 다음에 DJ가 나가도 서버 자동 진행이 맞게 돌아갑니다.

### 3.3 서버 “다음 곡” 시점 조정

- 지금은 `elapsed >= duration + 4초` 로 되어 있어서, **한 곡이 끝나고 4초 뒤에** 다음 곡이 나옵니다. 그래서 4초 공백이 들립니다.
- **곡 길이를 정확히 넣었다면**:  
  `elapsed >= duration` (또는 `duration - 0.5` 정도로 살짝 앞당기기) 로 바꾸는 편이 자연스럽습니다.  
  “4초 버퍼”는 잘못된 길이로 너무 일찍 넘어가는 걸 막으려는 용도라서, **길이를 정확히 쓰면** 버퍼를 줄이거나 제거해도 됩니다.

### 3.4 리스너: 전환 시 끊김 줄이기

- **같은 `<audio>` 요소를 유지**하고 `src`만 바꾸면, 리마운트보다는 약간 나음.  
  `key={audioStreamUrl}` 로 매번 새 요소를 만드는 대신, `key`를 제거하고 `src={audioStreamUrl}` 만 바꾸고, `onLoadedMetadata` / `onCanPlay`에서 `currentTime = 0`(또는 서버에서 받은 `elapsedSeconds`) 설정 후 `play()` 하면, “다음 곡” 전환이 조금 더 예측 가능해집니다.
- **다음 곡 미리 로드**: 현재 곡이 N일 때, 백그라운드에서 N+1번 곡 URL을 미리 로드해 두고(새 `Audio` 인스턴스나 `fetch`), 서버에서 `radio_now_playing`으로 N+1이 오면 이미 로드된 소스로 바로 재생하면 **체감 끊김**이 줄어듭니다.
- **완전한 무 gap**을 원하면, 결국 **서버에서 한 개의 연속 스트림(예: HLS 세그먼트)** 으로 믹싱해서 보내고, 클라이언트는 그 URL 하나만 재생하는 방식이 필요합니다. 작업량이 크므로, 우선은 “정확한 곡 길이 + 서버 단일 시점 + 같은 audio 요소 유지 또는 preload”까지만 해도 큰 개선입니다.

### 3.5 DJ가 “지금 곡 끝남”을 한 번만 알리기

- DJ 앱에서 재생 중인 `<audio>`에 `ended` 리스너를 두고, 한 번만  
  `PATCH /api/radio/channels/:slug`  
  `{ nowPlayingMusicId: 다음곡ID, nowPlayingStartedAt: new Date().toISOString(), queueMusicIds: [...], queueDurationsSeconds: [...], currentTrackDurationSeconds: 방금 끝난 곡의 실제 duration }`  
  를 보내게 하세요.
- 서버는 이걸 받으면 DB만 갱신하고 `radio_now_playing` 브로드캐스트.  
  그러면 “DJ가 있을 때”는 **끝나는 순간**에 다음 곡으로 맞춰지고, “DJ가 나간 뒤”에는 서버 타이머만으로 같은 로직이 이어집니다.

---

## 4. 체크리스트 (순서대로 적용 권장)

1. **곡 길이**: DJ가 곡 시작/메타데이터 시 `currentTrackDurationSeconds` + `queueDurationsSeconds` 를 항상 서버에 보내고, 서버가 `playlistSnapshot.durationsSeconds`와 자동 진행용 duration으로 사용하는지 확인.
2. **서버 전환 시점**: `duration + 4초` 대신, 정확한 `duration`(또는 `duration - 0.5`) 기준으로 다음 곡 전환하도록 수정.
3. **단일 주체**: 다음 곡 전환은 서버(또는 DJ의 한 번의 PATCH)에서만 이루어지고, 리스너 쪽 `onEnded` 등은 UI/상태만 쓰고 “다음 곡으로 바꾸는 로직”은 쓰지 않기.
4. **리스너**: `<audio>`는 key로 리마운트하지 말고 src만 바꾸기 + (가능하면) 다음 곡 preload.
5. **(선택)** 장기적으로 무 gap이 필요하면, 서버 측 연속 스트림(예: HLS) 설계 검토.

---

## 5. 한 줄 요약

- **“한 곡 끝나고 다음 곡이 자연스럽게”** 하려면:  
  **(1) 곡 길이를 DJ가 항상 정확히 보내게 하고**,  
  **(2) 다음 곡으로 넘기는 시점은 서버(또는 DJ PATCH) 하나만 쓰고**,  
  **(3) 서버는 저장된 정확한 duration으로 전환 시점을 계산하며**,  
  **(4) 리스너는 전환 시 같은 audio 요소 + 가능하면 다음 곡 preload** 로 끊김만 줄이면 됩니다.

이 순서로 하나씩 적용해 보시고, 특히 **곡 길이**와 **서버 전환 시점**부터 맞추는 것을 권장합니다.
