# 송출 상태 동기화(Race Condition) 조언 검토

> 외부 조언(낙관적 락, DJ WS 무시, 모바일 자동재생)을 코드 기준으로 검토한 문서입니다.  
> **아래 세 가지 조치가 코드에 반영되어 있습니다.**

---

## 1. DJ 수동 PATCH와 서버 자동 갱신의 충돌

### 조언 요약
- **문제**: DJ의 `advanceToNextTrack` 호출 시점과 서버 `setInterval`(2초마다) 자동 진행 시점이 겹치면, 곡이 두 번 넘어가거나 이전 곡으로 덮어쓰일 수 있음.
- **해결**: 낙관적 락 또는 Timestamp 검증. PATCH 시 **현재 재생 중인 trackId**를 함께 보내고, 서버의 현재 상태와 일치할 때만 업데이트.

### 현재 코드 상태
- **서버 `advanceToNextTrack`** (`server/routes.ts` 2995~3030행):  
  `bodyAdvanceToNextTrack`만 보고 바로 다음 곡으로 갱신 후 `updateRadioChannel` + `broadcastToRadioChannel` 호출.  
  **클라이언트가 “지금 끝난 곡 ID”를 보내지 않음.**
- **서버 `setInterval` 자동 진행** (3148~3202행):  
  `elapsedSec >= dur + 0.5`일 때만 다음 곡으로 갱신.  
  **DJ PATCH로 방금 갱신된 채널을 다시 읽어서 한 번 더 진행하는 일은 없지만**, 동시에 PATCH와 setInterval이 같은 채널을 건드리면 이론상 충돌 가능.

### 검토 결론
- **조언 타당함.**  
  PATCH에 `currentTrackId`(또는 `nowPlayingStartedAt`)를 넣어, 서버 DB의 `nowPlayingMusicId`(및 시작 시각)와 일치할 때만 `advanceToNextTrack` 로직을 실행하도록 하면, 이중 진행·덮어쓰기 방지에 도움이 됨.
- **구현 제안**
  - 클라이언트: `advanceToNextTrack: true`와 함께 `currentTrackId: 끝난_곡_ID` (또는 `expectedNowPlayingMusicId`) 전달.
  - 서버:  
    - `bodyCurrentTrackId !== ch.nowPlayingMusicId` 이면 “이미 다른 곡으로 바뀐 상태”로 간주하고 **진행하지 않고** 현재 채널 정보만 200으로 반환.  
    - 일치할 때만 기존처럼 다음 곡 계산 → `updateRadioChannel` → broadcast → `return res.json(updated)`.

## 2. WebSocket `radio_now_playing`과 DJ UI의 이중 처리

### 조언 요약
- **문제**: DJ UI도 같은 채널 구독자라 `radio_now_playing`을 수신.  
  `onMonitorEnded` → PATCH → 서버 브로드캐스트 → DJ UI가 같은 곡을 다시 로드 → 불필요한 재로드 또는 타이밍에 따른 꼬임.
- **해결**: 자신이 보낸 업데이트로 인한 소켓 이벤트는 무시하거나, isDJ 플래그로 모니터 오디오 로직을 분리.

### 현재 코드 상태
- **DJ UI** (`client/public/radio-dj-ui-mockup.html` 1961~1969행):  
  `radio_now_playing` 수신 시 `lastAdvancedMusicId === musicIdNum && (Date.now() - lastAdvancedTime) < 3000` 이면 **같은 곡을 3초 안에 이미 우리가 advance 응답으로 로드했으면** `loadMonitorAudioForTrackId` 호출을 **스킵**함.
- 즉, “자신이 보낸 PATCH에 대한 브로드캐스트로 인한 중복 로드”는 이미 일부 완화되어 있음.

### 검토 결론
- **조언 방향 맞음.**  
  “자신이 유발한 `radio_now_playing`은 모니터 로드에서 제외”하는 개념이 이미 `lastAdvancedMusicId`/`lastAdvancedTime`으로 구현되어 있음.
- **보완 제안**
  - 3초 창이 짧다면 5초 등으로 늘리거나,
  - “방금 PATCH 보냈는지” 플래그(`weJustSentAdvance`)를 두고, `radio_now_playing` 수신 시 해당 플래그가 true면 로드 스킵 후 플래그 해제하는 방식으로 더 명시적으로 “자신이 보낸 이벤트”만 무시할 수 있음.
  - isDJ 플래그로 “DJ일 때는 `radio_now_playing`으로 모니터 로드하지 않고, 수동 재생/advance 응답에만 반응”하게 분리하는 것도 일관성 있는 설계.

## 3. 모바일 자동 재생 정책 (Autoplay Policy)

### 조언 요약
- **문제**: 모바일 브라우저는 사용자 제스처 없이 `streamUrl`만 바뀌며 재생되는 것을 차단.  
  `radio_now_playing`은 오지만 소리가 안 남.
- **해결**: 리스너가 **최초 1회 “라디오 듣기” 버튼**을 눌렀을 때 오디오 객체를 생성(Resume)해 두고, 이후에는 **src만 교체하고 play()**를 호출.

### 현재 코드 상태
- **리스너** (`client/src/components/GlobalRadioPlayer.tsx`):  
  - `streamUrl`이 설정되면(WebSocket/refetch로) **한 번의 오디오**에 `inactive.src = streamUrl`, `load()`, `oncanplaythrough`에서 `play()` 호출.  
  - “청취하기” 버튼은 `setStream`(또는 `requestPlay`)을 호출하는 쪽에 있을 가능성이 높고, 그 시점과 `play()` 호출 시점이 **같은 사용자 제스처 체인 안에 있지 않을 수 있음** (비동기 로드 후 `oncanplaythrough`에서 `play()`).
- **송출실(모바일)**  
  - 모바일/제스처 없음일 때는 **활성 모니터에만** 로드하고, “모니터 재생” 버튼을 한 번 눌러야 소리 나도록 이미 처리됨.

### 검토 결론
- **조언 타당함.**  
  모바일에서는 `play()`가 **사용자 제스처와 동기적으로** 호출되어야 할 때가 많음.  
  현재는 `streamUrl` 변경 → effect에서 로드 → `oncanplaythrough`에서 `play()`라서, 제스처와 `play()` 사이에 비동기 간격이 있음.
- **구현 제안**
  - “라디오 듣기” / “청취하기” 클릭 시:
    - **즉시** `new Audio()` 또는 기존 오디오에 `src` 설정 후 **같은 이벤트 루프 안에서** `audio.play().catch(() => {})` 한 번 호출해 “재생 시도”를 등록하고,
    - 이후 `streamUrl`이 바뀔 때는 **src만 바꾸고** `load()` → `oncanplaythrough`에서 `play()` (이미 한 번 재생 시도가 있으면 정책 통과에 유리).
  - 또는 “청취하기”를 누른 직후 `streamUrl`이 설정되면, 그 클릭 핸들러 안에서 `setStream` 호출 직후 `requestAnimationFrame`/`setTimeout(0)`으로 **한 번** `audioRef.current?.play().catch(...)`를 호출해, 가능한 한 제스처 직후에 play를 시도하도록 할 수 있음.
